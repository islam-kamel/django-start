# 1.1.6 Characterization Suite and Test Infrastructure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Establish a deterministic, comprehensive characterization test suite for `django-start` 1.1.6 and fix repository test infrastructure without modifying production code (`djstartlib/`), packaging metadata, or runtime dependencies.

**Architecture:** Isolate test execution into a standalone `pytest.ini` with `pythonpath = .` and exact pinned runner `pytest==8.3.4` in `requirements-test.txt`. Organize characterization into layered unit and mocked-boundary integration tests under `tests/` using hermetic filesystem and boundary mocking, capturing observable contracts in `docs/baseline-1.1.6.md`.

**Tech Stack:** Python 3.11 canonical baseline, `pytest==8.3.4`, Click `CliRunner`, `unittest.mock`.

## Global Constraints

- Keep `djstartlib/` completely immutable.
- Do not modify `pyproject.toml`, packaging metadata, or runtime dependencies.
- Repository evidence must determine infrastructure choices. Never select modern-default tooling first and then constrain the legacy baseline to accommodate it.
- Strict minimal intervention for `.gitignore`: remove only demonstrably interfering rules (`*test*`, `test_*`) while retaining rules that do not interfere (`test/`).
- Exact `==` pins for test infrastructure (`pytest==8.3.4`); do not use open-ended `>=` constraints in baseline requirements, and do not manually pin modern transitive dependencies that invalidate historical compatibility.
- No normal characterization test may depend on live network access, PyPI, developer-machine state, global packages, or persistent filesystem state.
- Do not classify suspected behavior as a defect until reproduced by code and/or a reproducible test. The `sum(var_int)` arithmetic flaw is classified as a `known-defect`.
- Accurately classify `test_scaffold_orchestration.py` as a mocked-boundary orchestration integration test.
- Derive expected test counts from the implemented/collected suite (`pytest --collect-only -q`) rather than manually assumed.
- Do not use em dash characters anywhere in generated text.

import pytest
from djstartlib.models.utils.environment import Environment


def test_environment_initialization(monkeypatch, tmp_path):
    monkeypatch.setenv("PYTHONEXEC", "/custom/bin/python")
    monkeypatch.setenv("DJANGOADMIN", "/custom/bin/django-admin")
    monkeypatch.chdir(tmp_path)

    env = Environment(app="blog", project="mysite")
    assert env.get_app_name() == "blog"
    assert env.get_project_name() == "mysite"
    assert env.get_workdir() == str(tmp_path)
    assert env.get_exec() == "/custom/bin/python"
    assert env.get_django_admin() == "/custom/bin/django-admin"
    assert env.line_list == []


def test_environment_file_operations(tmp_path):
    sample_file = tmp_path / "sample.txt"
    sample_file.write_text("line 1\nline 2\nline 3\n", encoding="utf-8")

    env = Environment()
    lines = env.read_file(str(sample_file))
    assert lines == ["line 1\n", "line 2\n", "line 3\n"]
    assert env.index("line 2\n") == 1

    env.insert_line("line 2\n", "line 1.5\n")
    assert env.line_list == ["line 1\n", "line 1.5\n", "line 2\n", "line 3\n"]

    env.replace_line(2, "line 2 updated\n")
    assert env.line_list == [
        "line 1\n",
        "line 1.5\n",
        "line 2 updated\n",
        "line 3\n",
    ]

    output_file = tmp_path / "output.txt"
    env.write(str(output_file))
    assert (
        output_file.read_text(encoding="utf-8")
        == "line 1\nline 1.5\nline 2 updated\nline 3\n"
    )
