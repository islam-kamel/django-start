# Specification: 1.1.6 Characterization Suite and Test Infrastructure

## 1. Objective

Establish a deterministic, comprehensive characterization test suite for `django-start` version 1.1.6 and fix repository test infrastructure, adhering strictly to the principle of minimal intervention:
- `djstartlib/` remains completely immutable.
- `pyproject.toml` and `setup.cfg` packaging metadata remain untouched.
- Test infrastructure is isolated using a standalone `pytest.ini` and `requirements-test.txt`.
- `.gitignore` is fixed with strict minimal intervention: remove only the semantic rules that demonstrably interfere (`*test*`, `test_*`), retaining all rules that do not interfere (including `test/`).
- A comprehensive Behavior Contract Matrix is documented in `docs/baseline-1.1.6.md`.

---

## 2. Core Reasoning Principle

**Repository evidence must determine infrastructure choices. Never select modern-default tooling first and then constrain the legacy baseline to accommodate it.**

---

## 3. Runtime Strategy & Dependencies

### 3.1 Canonical Characterization Environment
The repository currently declares `python_requires = >=3.7` and explicitly classifies Python 3.7 through 3.11 as supported.
- **Canonical Characterization Target**: Python 3.14 on macOS arm64 (current verified runtime).
- **Tooling Compatibility**: Test tooling must be compatible with the baseline rather than forcing the baseline to accommodate modern tooling.
- **Dependency Pins**: Use exact `==` pins in `requirements-test.txt`. Never use open-ended `>=` constraints in the reproducible baseline requirements.
- **Minimal Initial Tooling**: Only include the test runner (`pytest==9.1.1` and its pinned runtime dependencies). Omit `pytest-cov` from the initial test dependencies; coverage tooling will only be introduced when justified in a separate change.

`requirements-test.txt`:
```text
iniconfig==2.3.0
packaging==26.3
pluggy==1.6.0
pygments==2.21.0
pytest==9.1.1
```

## 4. Infrastructure Design

### 4.1 Git Configuration (`.gitignore`)
Demonstrable interference analysis:
- `*test*`: Demonstrably prevents `tests/`, `pytest.ini`, and `requirements-test.txt` from being tracked. MUST be removed.
- `test_*`: Demonstrably prevents conventional test modules (e.g. `test_cli.py`). MUST be removed.
- `test/`: Matches only a directory named `test/`. Does NOT interfere with `tests/`. MUST be retained.
- Existing specific test ignore rules (`htmlcov/`, `.tox/`, `.nox/`, `.coverage`, `.coverage.*`, `.pytest_cache/`, `cover/`) MUST be retained.

### 4.2 Test Runner Configuration (`pytest.ini`)
A standalone `pytest.ini` at repository root:
```ini
[pytest]
pythonpath = .
testpaths = tests
addopts = --strict-markers --strict-config
xfail_strict = true
markers =
    integration: tests exercising end-to-end orchestration or external boundaries
```
This isolates test configuration completely from `setup.cfg` and `pyproject.toml`.

## 5. Characterization Test Architecture

Tests are structured under `tests/` in two distinct layers:

```text
tests/
├── conftest.py
├── unit/
│   ├── test_cli.py
│   ├── test_version.py
│   ├── test_environment.py
│   ├── test_project_manager.py
│   ├── test_app_manager.py
│   └── test_helper.py
└── integration/
    └── test_scaffold_orchestration.py
```

### 5.1 Test Principles
1. **Observable Behavior Priority**:
   CLI behavior
   → generated filesystem structure
   → settings/URL/template mutations
   → exit codes and stdout/stderr
   → error and duplicate handling
   → public Python interfaces
   → internal primitives only when testing them protects a meaningful contract.
2. **Deterministic & Isolated**:
   - Every file-modifying test operates inside a pytest `tmp_path` fixture with a controlled working directory.
   - No normal characterization test may depend on live network access, PyPI, developer-machine state, global packages, the developer's real virtualenv, or persistent filesystem state.
   - External network boundaries (`urllib.request.urlopen`) and subprocess calls (`subprocess.call`) are mocked in unit tests to eliminate external dependencies.
3. **Reproduce Before Classifying**:
   - Suspected behavior (e.g. whitespace assumptions, shell execution behavior, version-check arithmetic) will not be classified as a defect until reproduced by code and/or a reproducible test.
   - Discovered behaviors are classified into:
     - `intended`: Documented/expected behavior of 1.1.6.
     - `legacy-reliance`: Observable behavior that users or existing workflows may rely on.
     - `known-defect`: Demonstrably broken behavior under specific inputs.

## 7. Documentation Deliverable (`docs/baseline-1.1.6.md`)

The baseline document will include:
1. Environment and historical platform assumptions of 1.1.6 (Python version target, packaging setup).
2. The complete Behavior Contract Matrix.
3. Observed defects and quirks reproduced by the test suite (e.g. `sum(var_int)` version comparison flaw, `line_list.index("]\n")` fragility if formatting differs, unescaped shell commands).
4. Safety net guarantees for upcoming 2.0 modernization.
